## New issuer architecture and custody

### Custody acceptance must precede creation

Proposed private namespace: a fresh, random issuer ID under the Owner's WSL ~/.local/share/secure-file-drop/local-pki/. It must be disjoint from OLD_TLS/OLD_ISSUER and all previous contexts. Directory 0700, files 0600, Owner UID, no symlinks/hardlinks/unexpected mount points; verify actual effective access and Windows/WSL boundary, not mode text alone. This is a single-user threat model, not protection from an already compromised Owner/root account.

Observed OpenSSL3.0.13/binary hash is an inventory fact, not approval of that build for new cryptography. Future implementation review must verify the exact vendor package/security support, advisory status, executable/provider pins and profile behavior before creation.

The Owner must first select an existing approved local password manager or offline sealed recovery record and a distinct approved encrypted backup location. No such recovery medium is currently verified. A locally generated uniform 32-character secret from a 64-symbol alphabet supplies a proposed 192-bit secret; generator and custody procedure require review before use. Never reuse chat-supplied candidates or the unknown old passphrase. The agent must not generate, see, record or transfer the secret.

Propose an encrypted PKCS#8 CA key, RSA3072/SHA256, PBES2/AES256-CBC, PBKDF2-HMAC-SHA256 with at least 600000 iterations, calibrated upward on the target before adoption. This iteration floor is a design choice, not a measured performance claim. [OpenSSL PKCS#8 options](https://docs.openssl.org/3.0/man1/openssl-pkcs8/) define the selected encryption/iteration controls. Authentication/integrity of stored ciphertext also requires a private reviewed manifest, ownership and verified backup; do not treat CBC as authenticated encryption.

A future reviewed native TTY workflow reads the encryption passphrase with echo disabled, without transcripts, argv/environment values, redirected secret files, clipboard, stdout or parent-process capture. Plain key output may travel only through a bounded anonymous pipe from generation into encryption; no plaintext temporary file. Both processes must succeed, output uses exclusive creation, and failures retain a private receipt and partial ciphertext with no automatic retry. This is an I/O design, not executable key-generation code. [OpenSSL passphrase documentation](https://docs.openssl.org/3.0/man1/openssl-passphrase-options/) supports local hidden prompting; the proposed helper must prove its own terminal and non-disclosure behavior with future disposable fixtures.

After authorised creation, close the first terminal and reopen the new encrypted key using credentials recovered from the retained custody record, not remembered/reused process state. Public-only comparison must prove key consistency and exact new root SPKI. Independently restore the new encrypted key and issuer ledger into a separate private test directory from its backup and repeat the recovered-credential/public-identity check. The native secret interface must not screenshot, log or send the passphrase to an agent. Record only success/failure and public identities.

Require two verified ciphertext/ledger copies on distinct physical locations, including approved encrypted offline media; passphrase custody separate from key backup. Owner confirms physical separation and recovery entry accessibility; that attestation is distinct from automated file/ACL/hash/restore evidence. A named second custodian with separate sealed access is recommended if the Owner has one, but none is invented. Without recoverable credentials and a tested second location, stop before trusting the root. No new cloud service, security setting or paid vault is assumed.

Only future NEW encrypted CA key bytes may be copied by the authorised custody workflow. Never read/copy/export/re-encrypt the old key. CA key stays outside Docker, proxy mounts, public directory, repository and ZIP. The new server key needs separate restrictive runtime custody and encrypted backup; it is unencrypted only in the private runtime directory for unattended proxy reads, mounted read-only. Restore acceptance includes server public-key match. No CA key is ever in an application image.

### Independent identity/profile

These are proposed policy values, not existing certificates. Use distinct subject including new issuer ID, RSA3072/SHA256 key pair, independent empty issuance database and a fresh random positive 128-bit serial seed. No old subject/SPKI/key reuse, cross-signing, imported old V/R rows, serial/counter edits or old-root chain.

| Object | Proposed profile |
| --- | --- |
| Root | Self-signed, 730 days; critical basicConstraints CA:true,pathlen:0; critical keyUsage keyCertSign,cRLSign; SKI/AKI; no serverAuth EKU. Trust-anchor name constraints are not relied on to limit its Windows authority. |
| Server leaf | Separate new RSA3072 key; 90 days, bounded by root lifetime; critical CA:false; digitalSignature,keyEncipherment; EKU serverAuth only; SAN DNS:localhost, IP:127.0.0.1 and IP:::1 (encoded IPv6 loopback). No wildcard, LAN host/IP, clientAuth or other usage. |
| Revocation | X.509 v2 full CRL, SHA256/RSA signature, issuer exact match, AKI equals new root SKI, noncritical CRLNumber. Proposed first number 0x2000, next counter0x2001, independent sequence; no delta/indirect CRLs or old1001 replacement. |
| Distribution | Leaf's sole HTTP CDP: http://127.0.0.1:18082/sfd-local-ca-NEW_ISSUER_ID.crl. No HTTPS recursion, credential/query path, network-wide listener, AIA/OCSP dependency or old URL reuse. |

[RFC5280 certificate/CRL profiles](https://www.rfc-editor.org/rfc/rfc5280.html) govern extension encoding, issuer/authority identifiers and serial/CRL semantics. Exact SAN, KU, EKU, basicConstraints and chain validation must be checked on actual DER after future creation. A trusted root is account-wide signing authority regardless of this leaf's narrow SAN; software issuance policy and custody, rather than an assertion of root name-constraint enforcement, limit intended use.

Ledger transactions use a private lock, append-only operation receipts and immutable public artifacts by number/serial. Before signing, bind root/SPKI, config/source/binary, current ledger/counter, active leaf, issued/revoked serials, Owner authority and Aether exact review to a fresh one-use lease of at most 60 minutes. Consume lock before the sole attempt. On crash/partial output preserve all pre/post images; never decrement counters, overwrite signed CRLs, clear locks or retry automatically. A later forward-only repair requires review. Lost key/custody again means stop, not silently create another root.

## Signed CRL lifecycle and public endpoint

Propose validity of seven days, normal renewal by nextUpdate minus 72 hours (day four), warning at 48 hours remaining, critical at24 hours, and hard failure at expiry. Leaf renewal starts30 days before expiry (warnings14/7); root rotation starts90 days before expiry. Signing is a deliberate hidden local interaction, never an unattended unlocked CA. Validity must cover the whole approved operation plus six hours, and at least24 hours remaining; compute from fresh signed dates, not PR38's expired fixed RENEW_BY. Alert a missed renewal without changing verification rules.

Use a separately reviewed Windows-native public-only publisher/HTTP endpoint under a new Owner-profile public namespace, independent of Docker and WSL startup. This avoids making CDP availability depend on the engine whose cold start remains unsafe. Existing Python3.13 is a candidate runtime, not an installed service. Proposed binding is IPv4 loopback127.0.0.1:18082, fixed per-issuer path; recheck port ownership immediately before any separately authorised launch. Windows-to-WSL loopback assumptions are removed for CRL retrieval; future HTTPS preview still verifies its actual endpoint.

The publisher accepts at most1 MiB DER via an immutable staged public file. A pinned public root and native Windows CryptoAPI decoder/verifier must verify CRL signature, issuer, AKI, increasing number, thisUpdate/nextUpdate, allowed profile, current approved ledger snapshot and active-leaf non-revocation. [CryptVerifyCertificateSignatureEx](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptverifycertificatesignatureex) verifies CRLs with the issuer public key; implementation must check its actual Boolean result and errors, not merely process exit. This verifier is not yet implemented or accepted.

Publication sequence: private exclusive stage, complete verification, flush, retain immutable numbered DER/manifest, then atomic replace of same-volume public current DER; publish receipt only after readback. Server snapshots and re-verifies file before serving; it never serves unverified content during the gap between DER and manifest replacement. Crash recovery reconciles immutable receipt/DER forward; absent/mismatched state gives503, not fallback. Exporting public DER from WSL is separate from any private-key movement. The new endpoint never touches old publication.

HTTP permits only GET/HEAD of the exact path, static content-type application/pkix-crl, no listing, traversal, queries, upload, redirects or remote bind. Other requests give404/405; expired/missing/invalid CRL gives503. Small bounded public status messages and hash/date receipts disclose no secrets. No root/server keys, user configuration or sessions are in its directory. Binding via a normal loopback socket requires no URLACL or machine-wide service changes.

An untrusted local process can cause availability failures, but cannot mint a valid CRL without the issuer key. Windows can use a still-valid cached CRL during endpoint outage; a successful request then does not prove a new fetch. Require both current DER GET/readback and strict chain acceptance. Expired/unknown/offline status must not be suppressed. New issuer ID/CDP avoid collisions with the old cache; do not flush global caches or alter system clocks.

Propose separately approved per-user startup and hourly/login read-only monitoring, with public validity/hash/source checks and visible Owner alerts. No stored task password, elevated task, auto-unlock, auto-signing or automatic WSL/Docker startup. Actual startup reliability, login/session lifecycle and alert delivery must be demonstrated before transition; none is installed here.

## Failure, rollback and separate preservation gates

Before selection, a rejected creation/preview retains outputs privately, leaves live selection unchanged and removes only a newly added root if a separately approved rollback authorises it. Never automatically remove a trust anchor in use. No usable old-CA rollback is assumed.

After selection, prefer a verified previously accepted NEW-issuer leaf/config with a currently valid non-revoked CRL; CRL numbers never decrease. If unavailable, hold acceptance/service availability under the separately reviewed maintenance procedure and investigate forward. Do not restore the old leaf/root to claim secure recovery, disable revocation, roll back issuer counters or use an expired CRL. No database/schema/backups rollback is part of PKI rollback.

Any unexpected store/ref/file change, conflicting publisher, unknown consumer, failed signature/date/identity/ACL/restore test or insufficient margin stops dependent actions. Partial signing state is retained without auto-retry; new exact review resolves ambiguity.

PKI acceptance does not clear Docker cold-start, VHDX/ext4 recovery, persisted restart policy, current backup inventory, three-archive restoration, maintenance-window/scheduler, isolated database restore, ownership, schema12, image identity, traffic/IDLE or secure-input gates. Preserve accepted30-day retention,24-hour schedule and disabled file cleanup. No original backup timestamp/contents change, metadata downgrade, record reconciliation or rejected recovery image substitution. Historical disk hashes are dated receipts, not fresh verification.
