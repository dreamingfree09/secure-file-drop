## What functional separation would and would not establish

Microsoft documents that same-user WSL distributions can share a utility VM and do not form a security boundary from that user or its other distributions. Automount/interop settings are functional controls, not containment. Therefore a fresh root filesystem and socket can avoid normal application-path reuse, but cannot prove that Owner-readable original files and peer resources are inaccessible. This is a source-supported limitation, not an executed escape experiment. [Pinned upstream security model](https://github.com/microsoft/WSL/blob/1065a908203603e80d82573ff73cb58aa8df4f83/doc/docs/technical-documentation/security.md).

Installed-version source was inspected at WSL tag2.6.3, commit **eb7b0cff015998c199f62b2150c1cd8b5fcfe7b3**. DistributionRegistration.cpp stores an explicit distro/base-path identity; WslCoreVm.cpp constructs shared VM facilities, adds host-filesystem devices when configured, and can create/open/resize and attach the VM swap VHD (lines424-434/479-525). Version metadata and source inspection are not binary reproduction or a complete startup audit. No claim is made that starting one named distro inherently starts Docker Desktop or every registered distro. [Pinned VM source](https://github.com/microsoft/WSL/blob/eb7b0cff015998c199f62b2150c1cd8b5fcfe7b3/src/windows/service/exe/WslCoreVm.cpp).
