## Security assessment

SeaweedFS [security policy](https://github.com/seaweedfs/seaweedfs/blob/530be3e37337488ecc34d58441e0bc476e121c93/SECURITY.md) supports current releases and treats master, volume and raw filer as trusted internal services. Explicit credentials are essential; an unconfigured gateway is not a private bucket. The fixture disables console/optional IAM, Iceberg, Lance, SFTP/WebDAV and telemetry, binds master/filer/volume HTTP and gRPC to container loopback, and publishes only S3 on host loopback. Actual owned-container socket inspection verifies these bindings. S3 control gRPC uses the gateway bind address on port 19000: it is not host-published and remains restricted to this owned trusted bridge. Production needs an independently reviewed control-plane network/TLS design; do not attach untrusted containers.

All 25 [published SeaweedFS advisories](https://github.com/seaweedfs/seaweedfs/security/advisories) were inspected. Most declared affected ranges end before 4.48, including [S3 identity-cache mutation](https://github.com/seaweedfs/seaweedfs/security/advisories/GHSA-5fx4-c9qp-36jc), [POST policy enforcement](https://github.com/seaweedfs/seaweedfs/security/advisories/GHSA-qmx6-fpcw-q3xg) and [SFTP authentication](https://github.com/seaweedfs/seaweedfs/security/advisories/GHSA-q9rj-8p2j-whg4), all reported through 4.45. Several patched-version fields are empty, so a range alone is not proof of remediation. The pinned S3 gRPC source explicitly calls its admin-auth guard for identity mutation; no exploit was attempted.

[Filer TUS cross-prefix advisory GHSA-99q7-x53r-6j4g](https://github.com/seaweedfs/seaweedfs/security/advisories/GHSA-99q7-x53r-6j4g) has an open-ended affected range starting 4.39 and no patched-version value. The [upstream correction](https://github.com/seaweedfs/seaweedfs/commit/ce82e3a057080162a9fba11889157d2255815f71) and [follow-up hardening](https://github.com/seaweedfs/seaweedfs/commit/fa549e9c83b7799d512157d728f52052912831af) are in the pinned source; its handler checks the stored session target, also observed in tag 4.40. This is confirmed corrected source with stale/ambiguous advisory metadata, not a verified runtime exploitation result. Raw filer/TUS is not exposed in this fixture. ## Operations and recovery requirements

SeaweedFS combines master allocation/raft metadata, volume object bytes/indexes, filer LevelDB namespace/bucket metadata and S3 credential/policy configuration in this small single-node fixture. All persistent component data must be recovered consistently; a filer namespace without volume bytes, or volume bytes without filer paths/policies, is insufficient. Configuration/credentials are independent recovery dependencies. A single node is not replicated or disaster-tolerant.

RustFS uses its own single-node storage/metadata/IAM layout under /data, with independently supplied root configuration; PostgreSQL remains the application's separate metadata/session/ownership authority. A live filesystem copy or a successful object GET alone does not establish recoverability. Fresh-volume cold restore and separate PostgreSQL logical restore are bounded synthetic checks, not a cross-host production disaster recovery rehearsal.

Modest fixtures are approximately 5 MiB plus normal <=1 KiB application uploads and bounded two-request concurrency. SeaweedFS growth is capped to four 32 MiB logical volumes after the fixture correction. No maximum-size, throughput, durability, multi-node quorum, rolling upgrade, disk exhaustion or production sizing claim follows. Both require Docker/Linux, writable product-owned data and synthetic test configuration (SeaweedFS uid 1000, RustFS uid 10001), with separate PostgreSQL and application/native runtime resources. The hosted acceptance does not measure peak RAM or establish production CPU/RAM/disk sizing; representative capacity/retention benchmarks remain required before sizing approval. Owner/Aether must assign security-update ownership, monitor upstream advisories/current supported releases, refresh immutable pins and repeat functional/permission/recovery scans before approving a vendor/version.

## Migration and rollback proposal — not executed

1. Separately approve the exact vendor/version, topology, security support and configuration. Resolve existing/manual PostgreSQL schema and historical ownerless rows without inventing owners. Inventory generated keys, status, stored byte counts and hashes; identify pending/ambiguous uploads and deletion outcomes. Approve a coherent recovery plan and rehearse it on synthetic fixtures.
2. Quiesce writes, cleanup/deletion and administrative changes; drain active uploads within documented budgets. Take independently recoverable database, old storage and required secret/configuration backups at one consistent application checkpoint. Preserve migration state and key/row ownership.
3. Copy logical objects through authenticated APIs into a new private destination. Preserve generated keys and required metadata, verify every key, byte length and independently calculated SHA-256 against both source bytes and PostgreSQL. Include empty files; do not rely on ETags for multipart integrity. Keep a reconciliation manifest and separately validate destination policies, anonymous denials and scoped credentials. Never mount an existing MinIO data directory into another storage product.
4. After independent readback/recovery approval, change endpoint/credentials only in a separately approved cutover. Keep old storage read-only and protected during the rollback window. Recheck readiness, ordinary/admin ownership, native hashing, signed downloads and a new synthetic upload before resuming writes. There is no approved cutover in this PR.
5. Before destination writes, rollback can restore the consistent source/configuration checkpoint. After destination writes or deletions, quiesce again and reverse-copy/reconcile those changes with coherent PostgreSQL state, verifying keys/sizes/hashes before switching back; a simple endpoint reversal can lose or resurrect data. If reconciliation cannot be proven, recover the approved checkpoint and explicitly account for later writes. Retire neither store until independent recoverability and the retention decision are approved.
